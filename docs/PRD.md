## 1. 一页结论

NiKConnect 不从零重写。现有 ZF Relay 项目已经由用户在 **一加 Ace 5 Pro + Nikon Zf** 上完成 PTP/IP 连接、照片列表、缩略图和 JPEG 原图下载，应作为第一实现底座。近期工作不是增加页面，而是完成 0.1.1 的真机回归，再依次补多选队列、分页、取消与必要的后台能力。

Z-Relay 双端逆向的价值是补齐证据，而不是复制其产品复杂度：

- Android 3.0.87 提供标准 PTP 操作码、统一事务、分块读取及 0x200F 回退等参考；其服务端授权、配额、PairIP 和 native 核心均不进入 NiKConnect。
- iOS 1.1（build 335）明确包含 NP3 文档、Picture Control 编解码、槽位读取/写入报告和预览等模块，是第二阶段滤镜功能的主要参照；但“存在模块”不等于具体写入字段已经真机验证。
- KIMI-CODE 原型用于交互和视觉讨论。近期只采用连接、图库、传输队列的相关设计；Live View、滤镜预览、作品集、地点与统计不是近期承诺。

## 2. 产品原则

### 2.1 小步快跑，按验收门推进

每个版本只解决一类主要问题。上一道真机验收门未通过，不用新功能掩盖旧问题。版本号可调整，验收顺序不可倒置。

### 2.2 真机证据优先

优先级为：**用户真机结果 > 当前项目源码与测试 > 静态逆向观察 > 开源项目实现 > 协议推断**。模拟器、loopback 和单元测试用于回归，不替代真机验收。

### 2.3 复用优先，不重写已跑通链路

优先复用旧项目的 PTP/IP 双通道、数据包编解码、事务串行化、分块下载、MediaStore 发布和会话生命周期管理。仅在有可复现问题或明确需求时修改。

### 2.4 本地优先

不建设账号、订阅、配额、云端同步或远程服务端。相机通信在手机与相机之间完成；不需要 Z-Relay 的服务端授权体系。

### 2.5 文件完整性高于表面速度

下载以原文件字节完整为成功标准。性能调整必须同条件对照；不为了“更快”取消事务校验、边界检查或残片清理。

### 2.6 会话隔离

`connectionId` / generation 是异步结果和断点数据的边界。跨连接不复用 object handle、缩略图、未完成任务或 `.part` 文件；迟到结果不得写入新会话 UI。

### 2.7 相机写操作后置

第一阶段只读相机。第二阶段 Picture Control 写入必须先读、先备份、由用户明确选择槽位，再写入、读回核对并支持恢复；不做静默覆盖。

### 2.8 不做伪需求清单

Live View、遥控拍摄、滤镜实时预览、作品集、社交分享、多品牌支持和多平台同步均不因“原型里有”或“别人有”而自动进入路线图。

## 3. 背景与已有基础

### 3.1 已确认的真机能力

旧项目 `PROGRESS.md` 记录：0.1.0 已完成 PTP/IP 初始化、照片列表、缩略图和 JPEG 原图下载，并由用户在上述设备组合验收。

当前工作树的 0.1.1 已修复 R1–R4 并补齐测试：19 项 JVM 测试、`lintDebug`、`assembleDebug` 通过。**这些修复尚未完成真机回归。** Git HEAD 仍是 0.1.0 的 `2bc3f43`，因此文档引用的是“当前工作树”，不是把未提交修改归入旧 commit。

### 3.2 当前明确边界

- 仅 JPEG 下载有用户真机验收；NEF/NRW 尚未验收。
- 当前图库实现读取最近 120 个对象，逐个获取 ObjectInfo。
- 当前为单张下载；批量队列、后台保活、自动重连和跨连接续传未形成已验收能力。
- 仅上述手机与 Nikon Zf 组合有真机证据；其他机型、固件和 Android ROM 不预设兼容。

### 3.3 原型与旧项目的关系

原型回答“界面如何组织”，旧项目回答“协议和下载如何跑通”。二者都不能替代对方：原型中的模拟数据不是功能完成度，旧项目的两屏 MVP 也不限制未来信息架构。

## 4. 用户、场景与成功定义

### 4.1 目标用户

首发只服务使用 Nikon 相机、希望通过 Wi-Fi 把照片导入 Android 手机的用户。首先满足开发者本人及现有测试设备，再以真实反馈扩展。

### 4.2 核心场景

1. 拍摄结束后，手机连接相机 Wi-Fi，打开 NiKConnect。
2. 用户看到分阶段的连接进度和明确的错误原因。
3. 图库先出现结构与占位，缩略图按需加载；用户查看大图并选择照片。
4. 用户下载 JPEG 原文件，看到真实进度；取消或断线不会留下相册半成品。
5. 重连后重新读取相机状态；只有同一连接内的断点可以继续。
6. 核心链路稳定后，用户可导入本地 NP3、读取并备份滤镜槽位，在明确确认后写入与恢复。

### 4.3 成功定义

- 下载文件与卡内源文件 SHA-256 一致。
- 断线、取消、退出不会把残片发布到相册。
- 新连接不会出现旧连接的照片、缩略图、任务或进度。
- 错误能定位到网络获取、TCP、握手、OpenSession、数据读取或保存阶段。
- 每个版本都有可重复执行的验收记录，而非只写“已优化”。

## 5. 目标与非目标

### 5.1 近期目标

- 稳定复用现有 PTP/IP 连接和 JPEG 下载链路。
- 完成 0.1.1 R1–R4 的真机验收。
- 提供多选、串行队列、取消和图库分页。
- 根据真实使用需求决定后台下载优先级。
- 为第二阶段 NP3 / Picture Control 建立独立技术验证，不阻塞基础导出。

### 5.2 非目标

- 不复刻 Z-Relay 的服务端、收费配额、授权校验或商业逻辑。
- 不做 FTP 第二通道、云相册、账号系统或社交分享。
- 不在首版支持 Canon/Sony 等多品牌，不承诺 iOS 客户端。
- 不做 NEF/NRW 解码、编辑或“RAW 美化”；RAW 阶段只处理原文件传输。
- 不把 Live View、遥控、视频工作流、滤镜预览、作品集列为近期交付。
- 不在尚未确认数据源前承诺尼康云创在线接口或自动同步。

## 7. 功能需求

### 7.1 连接与设备识别

| ID | 需求 | 验收要点 |
|---|---|---|
| C-01 | 引导用户连接相机 Wi-Fi，并区分“系统未连接”和“应用拿不到网络” | 设置引导与错误文案不混淆；处理 Android 10+ 网络请求行为 |
| C-02 | 复用活动 Wi-Fi；无 INTERNET 能力时通过 `requestNetwork(TRANSPORT_WIFI)` 获取 | 不假定相机网络有互联网；失败有超时和取消处理 |
| C-03 | host 候选依次为手动地址、Wi-Fi gateway、192.168.1.1，去重尝试 | 手动地址优先；每个候选有明确失败结果 |
| C-04 | 在指定 `Network` 上建立命令和事件通道，默认端口 15740 | socket 不漂移到其他网络；连接取消能终止等待 |
| C-05 | 完成 InitCommandRequest/Ack、InitEventRequest/Ack、OpenSession(1)、GetDeviceInfo | 显示制造商、型号、固件；SESSION_ALREADY_OPEN 按已开处理 |
| C-06 | 保留部分 Nikon Z 机身需要的 350ms TCP settle delay，后续只可基于对照实验调整 | 不以删除延迟作为未验证的“提速” |
| C-07 | 断线、超时、坏包或 transactionId 错配时关闭旧通道并使 generation 失效 | 下一次连接不继承旧 socket 或迟到数据 |

### 7.2 图库与看图

| ID | 需求 | 验收要点 |
|---|---|---|
| G-01 | 使用 GetObjectHandles 获取对象；当前基线为倒序最近 120 个 | 空卡、无权限、存储变化有明确状态 |
| G-02 | 使用 GetObjectInfo 解析文件名、大小、格式、拍摄时间、storageId 和 handle | 解析失败不阻塞其他照片；显示可诊断信息 |
| G-03 | 缩略图优先 NIKON_GET_LARGE_THUMB(0x90C4)，失败回退 GET_THUMB(0x100A) | 回退可用；失败显示占位，不重复死循环 |
| G-04 | 先展示列表和占位，再按可见区域懒加载；缓存按会话隔离 | 快速滑动的旧结果不回填到新位置或新会话 |
| G-05 | 0.2 增加分页/继续加载，而非一次遍历整张卡 | 超过 120 个对象仍可访问；记录每页耗时 |
| G-06 | 大图查看以已获取的预览为入口，下载是独立明确动作 | 不把预览当作原文件下载成功 |

### 7.3 下载、队列与文件完整性

| ID | 需求 | 验收要点 |
|---|---|---|
| D-01 | 使用 GetPartialObject(handle, offset, length) 分块读取；当前实现为 4MiB | 4MiB 是实现基线，不宣称为所有设备最优值 |
| D-02 | 同一 `PtpIpClient` 的事务保持串行，校验响应码、transactionId 和块边界 | 迟包、错配和空块直接失败并关闭通道，不拼接污染数据 |
| D-03 | 同 connectionId 内使用 `.part` 按 offset 续写；最终长度必须等于 ObjectInfo.size | 同会话中断后可续；跨连接不得续用 |
| D-04 | 通过 MediaStore `Pictures/<产品目录>` + IS_PENDING 发布；成功后清除 pending | 取消、失败和长度不符时不公开半成品；产品目录随命名迁移 |
| D-05 | 取消当前任务时关闭/取消对应 I/O，删除本次残片并保留已发布文件 | UI 最终状态与磁盘状态一致 |
| D-06 | 0.2 提供多选、串行队列、当前/等待/完成/失败状态和单项取消 | 不并发向同一相机发送命令；失败项不阻塞可继续的后续项 |
| D-07 | 显示已下载字节、总字节和当前文件名；速度仅在样本充分时展示 | 不用随机或虚假进度；取消后速度归零 |
| D-08 | 下载成功以长度校验为基础，验收以源文件 SHA-256 对照为准 | 测试报告保留样本、大小、哈希和设备/固件 |
| D-09 | 0.4 再启用 NEF/NRW 原文件导出；失败时明确标记未支持/未验证 | 不把 JPEG 成功推导为 RAW 成功，不做 RAW 解码 |

### 7.4 后台与系统资源（0.3，按需）

- 前台服务类型使用 `connectedDevice`，通知展示当前任务与进度。
- 下载期间持有 Wi-Fi Lock 与 Partial WakeLock，并在结束时成对释放。
- socket 必须绑定相机对应的 `Network`；后台切换网络时重新评估连接，而非静默漂移。
- 保存队列和当前 offset 仅用于同会话恢复；进程死亡后先重新识别相机对象，再决定是否重新开始。
- 国产 ROM 的后台限制以真机记录为准；不承诺绕开系统管控。

### 7.5 NP3 / Picture Control（第二阶段）

| ID | 需求 | 验收要点 |
|---|---|---|
| F-01 | 通过系统文件选择器导入本地 NP3，解析并校验格式 | 非法、损坏或未知版本有明确错误；不执行文件内任何内容 |
| F-02 | 读取相机当前 Picture Control 槽位、活动项与能力信息 | 显示真实读回结果；不支持机型不进入写入流程 |
| F-03 | 写入前备份目标槽位原始数据和必要元数据 | 备份可读回且与目标槽位绑定；无备份不写入 |
| F-04 | 用户明确选择目标槽位并确认后才写入 | 默认不自动覆盖；不批量写入 |
| F-05 | 写入后读回核对，并显示成功、字段不支持或校验差异 | 不以“已写入”代替字段级验证 |
| F-06 | 支持从备份恢复原槽位 | 恢复后再次读回；失败保留备份与诊断信息 |
| F-07 | 优先验证 NP3 扩展字段和具体写操作码，不能假定 Android 版已有此能力 | iOS 类型名是线索；真实 opcode、字段布局和机型限制仍需函数/真机证据 |
| F-08 | 云创数据来源只有在接口、授权与文件格式被实际确认后才排期 | 未确认前只支持本地 NP3，不虚构云端 API |

**滤镜预览不是该阶段的验收前提。** 如未来增加预览，必须标注“近似渲染”或“相机实取预览”的来源，不能混用。

## 8. 交互与原型约束

### 8.1 近期采用的界面

- **连接页**：Wi-Fi 引导、分阶段握手、设备信息、错误详情和重试。
- **图库页**：最近照片、缩略图、选择、大图查看和分页。
- **传输队列**：当前任务、等待任务、真实字节进度、取消和失败原因。

### 8.2 原型中暂不作为需求的部分

Live View、参数拨盘、远程快门、滤镜 GPU 预览、作品集、地点分组和年度统计均保留为概念探索。原型中的相机型号、照片、速度、完成状态为模拟数据。

### 8.3 视觉参考

可沿用暖调深灰、低饱和强调色、等宽数字、克制的圆角和明确焦点态。视觉 polish 不得先于真机稳定性；375px 等小屏需要单独检查纵向空间、折行和预览高度。

附件：`prototype/index.html`。运行方式见 `prototype/README.md`。

## 9. 技术架构与复用边界

### 9.1 模块职责

| 模块 | 责任 | 当前参考实现 |
|---|---|---|
| `ptp/` | 小端编解码、PTP/IP 数据包、事务、数据集、操作码与响应码 | `PtpPackets.kt`、`PtpIpClient.kt`、`PtpDatasets.kt` |
| `camera/` | Wi-Fi 获取、候选地址、会话资源、分块下载、MediaStore | `CameraNetwork.kt`、`CameraRepository.kt`、`PhotoDownloader.kt` |
| `ui/` | 页面状态、用户操作、会话 generation、错误展示 | `SessionController.kt`、Compose 页面 |
| `picturecontrol/`（未来） | NP3 解析、槽位模型、备份、写入和读回 | 新模块；不得挤入下载事务的隐式副作用 |

### 9.2 关键实现事实

- `PtpPackets.kt` 已包含双通道初始化、操作请求/响应、数据包及当前所需操作码。
- `PtpIpClient.kt` 使用 `Socket(Proxy.NO_PROXY)`、4MiB receive buffer、TCP_NODELAY、keepAlive、30s socket timeout、10s connect timeout；事务以 `@Synchronized` 串行。
- `CameraRepository` 和 `SessionController` 使用 generation 管理旧资源与迟到异步结果。
- `PhotoDownloader` 的 `.part` 文件名绑定 connectionId、handle、大小和安全文件名，从结构上防止跨连接续传。

### 9.3 修改约束

- 协议常量或分块逻辑变化必须增加对应 JVM 测试和真机对照。
- UI 不直接解析 PTP 字节，不自行启动第二套 socket。
- 新会话创建时关闭旧 client、取消旧 job、释放 network callback 和系统锁。
- 第二阶段滤镜命令与下载命令共享同一串行相机通道，不能并发交错。

## 10. 数据、隐私与本地存储

- 不收集账号、联系人、广告标识或云端行为数据。
- 图库索引、缩略图缓存和任务状态仅保存在本地，并按会话清理或失效。
- 日志保留设备型号、固件、操作码、响应码、字节数和错误阶段；避免记录不必要的个人信息。
- 原文件通过 MediaStore 写入用户选择的相册位置；残片位于应用可管理的临时区域。
- NP3 备份保存在本地，包含来源、目标槽位、时间和校验信息；不得自动上传。

## 11. 兼容性、性能与可观测性

### 11.1 兼容性

- 首个支持基线：Android 10+，一加 Ace 5 Pro + Nikon Zf。
- 旧项目技术配置为 Kotlin/Compose、minSdk 29、target/compile 35、JDK 17；迁移项目时可升级，但需单独记录，不与功能改动混在一个验收批次。
- 新设备或固件必须有自己的连接、列表、缩略图和下载记录，不能仅凭“也是 Nikon Z”标记兼容。

### 11.2 性能

- 当前图库逐个 GetObjectInfo，120 个对象会受往返延迟影响；先做懒加载和分页，再用数据决定是否引入批量扩展。
- 当前下载分块为 4MiB；Z-Relay Android 另有 1024KiB 实现。二者都是参考点，不是普遍最优常数。
- 性能报告至少记录对象数、文件大小、分块大小、手机/相机/固件、距离/网络条件和总耗时。
- 内存应按分块和流式写入控制，不把整份 RAW 或视频一次性读入内存。

### 11.3 可观测性

连接页和导出诊断至少能区分：网络获取、TCP 建连、InitCommand、InitEvent、OpenSession、GetDeviceInfo、ObjectHandles、ObjectInfo、Thumb、PartialObject、MediaStore。失败时保留阶段和原始响应码。

## 13. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 0.1.1 修复只通过 JVM，未真机回归 | 基础稳定性被高估 | 将真机回归设为所有新功能的入口门 |
| 相机 Wi-Fi 无互联网且系统网络切换 | socket 漂移、后台中断 | 显式 Network 获取与绑定，记录 ROM 差异 |
| 相机单连接、命令串行和迟包 | 数据错配、队列污染 | 单事务通道、generation、错配即关闭 |
| 逐个 ObjectInfo 较慢 | 大图库首屏等待 | 先占位/懒加载/分页；批量扩展另行验证 |
| NEF 与 JPEG 行为不同 | RAW 失败或内存压力 | 单独验收，不扩展未验证承诺 |
| NP3 扩展字段/写操作码不确定 | 滤镜写入不完整 | 先 B0 探针；备份与恢复；参考 iOS codec/camera 链 |
| 云创数据来源未确认 | 在线滤镜计划失实 | 只做本地 NP3，直到取得真实数据证据 |
| 原型范围大于产品阶段 | 开发分散 | 近期只实现连接、图库、队列；其余标记概念稿 |

## 14. 待确认问题与所需证据

1. **Zf 固件版本与当前 0.1.1 工作树真机结果**：先完成既有验收表。
2. **真实图库规模**：120、300 或更大，决定分页和批量元数据优化优先级。
3. **后台是否为当前痛点**：若只在主动导入时使用，可推迟前台服务与系统锁。
4. **RAW 文件类型与大小分布**：决定 0.4 样本和性能预算。
5. **NP3 写字段与机型能力**：需要 iOS 函数级证据、相机读取数据及一次可恢复的单槽测试。
6. **云创数据来源**：需要真实文件/接口/授权证据，在此之前不进入开发排期。
