## 7. 2026-11-14 追加：真机暴露的一个服务端硬约束

把已占用的槽位换成另一个方案，**不能只靠 `PATCH /camera/{guid}/{deviceId}`**：实测
`IF_IR_R_C004 -> 400`（响应体空）。原因是 `C003` 会先把方案自动塞进第一个空位，
于是 PATCH 里出现"同一方案两处"；而"换掉旧方案"在 PATCH 里又表现为移除，服务端同样拒绝。

正确顺序（已实现于 `CloudAddToCameraViewModel.addToSlot` 与 `planSlotWrite`）：

1. 目标位被别的方案占着 → `C005 DELETE` 删掉它；
2. 新方案已在别的槽位 → `C005 DELETE` 那一份，再 `C003` 重新加入（服务端会放到刚空出的低位）；
3. 重新取 `H13` 排布，`PATCH` 只发送"仍应存在的完整排布"（同一 id 只出现一次）。

改完后真机链路：`C003 200 → H13 200 → C005 200（旧方案）→ C005 200（重复那份）→ C003 201 → H13 200 → C004 200`。

## 9. 2026-11-14 追加：一次破坏性 bug（已修，0.8.5）

一加 Ace 5 上「把第 2 位下移一位再保存」触发：

```
IF_IR_R_C005 DELETE .../01M7A6M9SVH3WA02W4BS6RQXG6   -> 200   (Mate Film)
IF_IR_R_C005 DELETE .../01M7A67M26P4K3HMJYVQD8YY0E   -> 200   (Mid-Spring)
IF_IR_R_C004 PATCH {"recipes":[{"slotNo":1,...Mid-Spring},{"slotNo":2,...Mate}]} -> 400
```

结果：**相机槽位被清空**（`C002` 返回 `[]`）。根因是 `planSlotWrite` 把「同一槽位换了方案」当作替换，
一次**互换**被算成两次替换 → 两个方案都被删，随后 PATCH 引用已删的 id 必然 400。

修法（0.8.5）：

1. `planSlotWrite` 的删除判定改为**集合差**：只有「在编辑后彻底消失的方案」才进 `deletes`；互换不产生删除。
2. `saveLayout` 与 `CloudAddToCameraViewModel.addToSlot` 都加了**回滚**：一旦后续 PATCH 失败，
   把已删的方案用 `C003` 加回去，避免用户看到槽位被清空。
3. 新增两条回归测试：`swapping two slots never plans deletes`、`replacing the recipe of a slot plans one delete plus the new patch`
   （此前 133 项测试全绿却漏掉这个用例，这是"测试没覆盖语义"的典型）。

数据已用 curl 恢复到 `1 Mate Film / 2 Mid-Spring`（`C003 201` + `C004 200`）。
